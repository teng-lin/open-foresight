# Note service readiness and recovery

The original note producer at `0x100a2cf98–0x100a2d010` requests the LiteRT-LM service after emitting its scanning status and before loading transcript embeddings. A null or unready result logs a warning, awaits `abortAndResetOnDeviceService`, and requests the service once more. A second null/unready result performs the asynchronous installed-model lookup and throws the corresponding public error. Exceptions thrown by acquisition or reset propagate; later embedding, tokenizer, conversation, stream, and close failures do not enter this readiness retry.

`acquireNoteEnhancementService` implements that exact two-acquisition boundary. Application invokes it inside the recovered producer's `ensureReady` callback. It no longer silently returns merely because `domain.generator` is null. A producer with no pending notes can still return its merged prior content without acquiring a model, matching the original classification-before-readiness order.

The original public errors are:

- Installed model: `LiteRT-LM service is not ready. Please try again in a moment.`
- Missing model: `LiteRT-LM service is not ready: on-device inference model is not downloaded. Please check Settings -> Model Management.`

The service getter at `0x1009203e4` awaits `_ensureLiteRtLmReady`. The latter returns immediately for a ready singleton, otherwise awaits a shared initialization future and initializes again if that future finished without a ready service. Reset at `0x1008ef56c` awaits service shutdown, then clears the singleton, initialization future and cached initialization model/configuration. Domain now provides the corresponding ready fast path, shared pending initialization, registered-model load, owned runtime reset and rejection/cleanup of an obsolete candidate when the workspace closes. Native readiness uses `NativeRuntime.loaded`, which follows a successful native model probe and conversation creation. Fixtures explicitly declare readiness rather than relying on an unconfigured fake runtime.

The initializer's decompiled output omitted important native exception handlers. Bounded disassembly at `0x1008f0084–0x1008f04f4` establishes a distinct startup policy: after the first initialization error it clears model cache entries, recreates the same cache directory, awaits shutdown, constructs a fresh service and retries the same settings. A second error rethrows when vision was disabled. When vision was enabled, it makes a third attempt with vision disabled; this is a text-only fallback, not a GPU-to-CPU text backend fallback. That third attempt's failure logs, shuts down and nulls the service. Original model-path discovery, metadata refresh and model-specific vision configuration are separate from the outer note producer's single reset.

The cache helper at `0x1006698f4` scans the nonrecursive `model_cache` and `litert_lm_cache` support directories for files whose names start with the model basename or basename without extension. It also scans the model's parent directory, additionally requiring the filename to contain `_mldrift_` or `.xnnpack_cache`. The dynamic string operation is proven to be `String.contains` at `0x100d20a34`, not suffix matching. `_deleteFileWithRetry` permits five attempts, waiting 100, 200, 300 and 400 ms after the first four failures. Its fifth failure logs a warning and continues. The outer cache helper logs directory/list errors and returns; it does not make cache cleanup failure fatal to the startup retry.

The port uses its own model registry and owned runtime/cache locations. It never reads or modifies the original Foresight cache directories or configuration credentials. Source-built runtime packaging and actual production model/platform acceptance remain separate gates. Exact vision-enabled startup, model metadata refresh and actual Linux native runtime acceptance are not established by the Dart readiness adapter tests.
